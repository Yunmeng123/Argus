# Argus 产品路线图

## 产品定位

Argus 面向中小研发团队，提供可私有化部署、支持多代码托管平台的 AI 代码审查。核心价值不是“调用一次大模型”，而是把审查做成可度量、可追踪、可治理的工程流程。

## 北极星指标

- PR 审查覆盖率：进入主分支的 PR 中完成 Argus 审查的比例。
- 有效问题采纳率：被修复或确认的问题占全部发现的比例。
- P95 首次反馈时延：Webhook 到首条审查结果的时间。
- 误报率：被开发者标记为误报的问题占比。

## 需求优先级

| 优先级 | 需求 | 用户价值 | 验收指标 |
| --- | --- | --- | --- |
| P0 | Webhook 任务可靠性 | 平台抖动或服务重启不丢审查 | 已确认任务不丢；失败进入 DLQ；不可投递返回 503 |
| P0 | 任务可观测性与人工重放 | 运维可定位积压和失败任务 | 可查看队列状态、失败原因并安全重放 |
| P1 | 开发者反馈闭环 | 用真实反馈降低误报 | 支持“有用/误报”并进入评测集 |
| P1 | 规则与仓库策略 | 团队可按仓库控制严重级别和阻断标准 | 支持仓库级规则模板及阈值 |
| P1 | 增量审查与缓存 | 降低重复 Token 成本和响应时间 | 相同文件片段命中缓存；成本可量化 |
| P2 | 多租户与 RBAC | 支持团队化部署 | 项目隔离、角色授权、审计日志 |
| P2 | 趋势洞察 | 帮助负责人发现系统性质量问题 | 按仓库、团队、规则展示趋势 |

## 迭代拆分

### 迭代 1：可靠任务链路（本次）

- RabbitMQ 持久化 quorum queue。
- Publisher Confirm，只有 Broker ACK 后才返回 `queued`。
- 消费失败有限重试，耗尽进入 DLQ。
- Broker 不可用时 Webhook 返回 HTTP 503，促使代码平台重试。

### 迭代 2：任务运营台

- 新增任务状态表和任务查询 API。
- 看板展示 READY、RUNNING、FAILED、DLQ 数量和 P95 延迟。
- 支持带权限校验的单任务重放，记录操作审计。

### 迭代 3：反馈闭环

- 行级评论增加“有用/误报”反馈入口。
- 反馈与模型、Prompt、规则版本绑定。
- 每周自动生成离线评测报告，作为模型发布门禁。

## 产品评审结论

当前优先解决“结果是否可信”之前的“任务是否可靠”。如果 Webhook 已返回 202 但消息实际未被 Broker 接受，用户会永久缺失一次审查且难以察觉。因此 Publisher Confirm 和明确的 503 重试语义属于 P0，不应推迟到可观测性页面之后。
