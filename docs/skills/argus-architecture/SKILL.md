# Argus 架构规范

保持 Argus 为可维护的模块化单体，并在修改代码前提出最小且安全的设计。

## 从事实出发

1. 阅读 `README.md`、`pom.xml`、相关配置、接口、调用方、实现和测试。
2. 说明当前行为和具体问题，不得仅根据类名推断需求。
3. 列出受影响的包、公开契约、持久化数据、外部 API 和部署假设。
4. 当变更跨越模块边界时，给出备选方案及其取舍。
5. 除非已获得明确授权，否则在数据库迁移、公开 API 破坏性变更、服务拆分或大范围重构前停止修改并请求确认。

## 保持模块边界

- `diff`：解析 unified diff；保持其独立于 Web、LLM 和持久化逻辑。
- `context`：丰富审查输入；不负责审查流程编排。
- `review`：通过契约协调过滤、模型审查、验证、报告和通知。
- `llm`：适配模型提供方并统一模型输出；不包含 VCS 行为。
- `vcs`：验证 Webhook 并适配平台 API；平台差异必须封装在 `VcsProvider` 后面。
- `report` 和 `profile`：负责持久化和查询；不得调用 VCS 或 LLM 客户端。
- `web`：校验并转换 HTTP 请求；不得在 Controller 中放置业务规则。
- `config`：负责配置快照和校验；不得跨边界暴露可变配置。

通过接口隔离基础设施细节。尤其不得让审查编排直接依赖 RabbitMQ、具体数据库或平台专用 HTTP 客户端。

## 作出架构决策

默认沿用现有模块化单体。只有存在可衡量的独立扩缩容、故障隔离、安全隔离或团队所有权需求时，才引入服务边界。

重大决策应新增 `docs/adr/NNNN-short-title.md`，并包含：

- 背景和约束
- 考虑过的方案
- 最终决策
- 影响和运维成本
- 迁移与回滚方案
- 验证策略

## 控制变更范围

- 优先扩展现有契约，不要在共享编排逻辑中添加平台判断。
- 默认保持 API、存储数据、配置键和消息结构的兼容性。
- 为持久化消息设置版本，并保证消费者具备幂等性。
- 对每个外部调用或异步边界，明确超时、重试、去重和失败恢复的职责归属。
- 不得将功能变更与无关的包移动、依赖升级、批量格式化或命名清理混在一起。

## 给出实施计划

编码前说明：

1. 现有流程以及缺陷或限制。
2. 建议的边界和需要修改的契约。
3. 预计修改的准确文件范围。
4. 兼容性、安全、并发和数据风险。
5. 测试方案和回滚路径。

编码后验证依赖方向未发生变化，或其变化已被有意记录，并总结所有剩余风险。
