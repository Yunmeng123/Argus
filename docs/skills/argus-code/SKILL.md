# Argus 代码规范

实施最小且完整的补丁，保持现有契约，并通过有针对性的测试证明行为正确。

## 修改前检查

1. 阅读仓库说明并检查 `git status`。
2. 阅读目标代码、直接调用方、实现的接口、相关配置和测试。
3. 可行时，先用失败测试复现或表达缺陷。
4. 确定最小文件范围，不得修改无关代码。

使用 `rg` 和有针对性的文件读取。不得扫描或编辑 `web/node_modules`、`target`、`data`、报告或生成的前端资源。

## 保持 Java 代码一致

- 使用 Java 17，并遵循现有包结构。
- 优先使用构造器注入，并使用不可变 record 表示值对象。
- 保持 Controller 精简，在边界处校验输入。
- 使用明确的领域异常或有意义的标准异常；不得静默吞掉失败。
- 明确处理 `null`、空白字符串、格式错误的外部载荷和缺失配置。
- 日志应便于排查，但不得包含令牌、密钥、完整签名载荷或敏感源码内容。
- 不得用 `try/catch` 包裹 import。

对于并发代码，应记录并测试幂等键、顺序、重复处理、关闭行为和失败恢复。避免使用任意时长的 sleep 编写基于时序的测试。

## 安全处理外部系统

- 将 GitHub、GitLab 和 Gitee 的细节保留在各自的 `VcsProvider` 实现中。
- 集中处理鉴权；API 支持请求头时，不得将凭据放入查询字符串。
- 在增加重试前定义连接/读取超时，并区分可重试的失败。
- 当行级评论无法定位时，保留汇总评论降级路径。
- 在自动化测试中使用 Stub 替代 VCS 和 LLM 调用；不得要求真实凭据。

## 保持 Vue 代码一致

- 后端调用统一通过 `web/src/api/`。
- 复用现有 Element Plus 组件和项目样式。
- 明确处理加载、错误、空数据和成功状态。
- 避免在多个视图中重复维护服务端状态或转换 API 错误。
- 保持响应式行为和键盘可访问交互。

## 测试与交付

1. 为每个修复的缺陷增加有针对性的回归测试。
2. 先运行范围最小的相关测试；后端变更还应运行 `mvn test`。
3. 前端变更应在 `web/` 目录运行 `npm run build`。
4. 检查最终差异中是否包含密钥、生成文件、范围蔓延或意外格式化。
5. 仅在行为、配置、架构或运维方式变化时更新文档。
6. 使用描述清晰的提交信息提交一个目标一致的变更。

如果验证受环境限制，应报告准确命令和限制原因；不得声称验证已通过。
